## Критичное

### 1. `rig.delete()` удаляет все objectSet в сцене, включая shadingEngine

[rig.py:160](../rig.py#L160) — **исправлено 2026-08-28**, `type` заменён на `exactType`

```python
for set in cmds.ls(type="objectSet"):
    if set not in ['defaultLightSet', 'defaultObjectSet', 'initialParticleSE', 'initialShadingGroup']:
        if cmds.objExists(set):
            cmds.delete(set)
```

Флаг `-type` в `cmds.ls` подбирает и производные типы. `shadingEngine` наследуется от `objectSet`, поэтому под удаление попадают все шейдинг-группы сцены, кроме `initialShadingGroup`. Туда же уходят пользовательские сеты выделения и сеты постороннего пайплайна.

`rig.delete()` вызывается при каждой загрузке рига из темплейта ([template.py:294](../template.py#L294)), то есть это обычный рабочий цикл, а не редкий сценарий.

**Что сделано:** `cmds.ls(type="objectSet")` заменён на `cmds.ls(exactType="objectSet")`. Флаг `exactType` берёт только ноды ровно этого типа, поэтому производные (`shadingEngine`, а также `displayLayer` и `animLayer`) больше не попадают под удаление. Заодно переименована переменная цикла `set` → `s`, она затеняла встроенный тип.

**Что осталось и почему не критично:** пользовательские сеты выделения — это ровно `objectSet`, и они по-прежнему удаляются вместе с ригом. Но настройка рига всегда идёт в чистой сцене (подтверждено 2026-08-28), посторонних сетов там не бывает, так что практического веса у остатка нет. Полное решение, если руки дойдут, — удалять только сеты рига: они все лежат внутри `sets` (см. `utils.create_default_sets()`, [utils.py:1252](../utils.py#L1252)) плюс `<модуль>_nodesSet`.

### 2. Данные хранятся в сцене через `pickle` — это исполнение произвольного кода

> **Решение 2026-08-28: отложено.** Направление согласовано (json вместо pickle), но не сейчас. Не предлагать повторно без запроса — вопрос уже разобран.

[utils.py:14](../utils.py#L14) `pyToAttr()` / [utils.py:45](../utils.py#L45) `attrToPy()`

```python
loadedData = cPickle.loads(stringAttrData.encode())
```

`pickle.loads` на данных из файла сцены — вектор RCE: подготовленная строка в строковом атрибуте выполняет произвольный питон при чтении. `pickle` вызывается **только внутри этих двух функций**; остальные 26 мест — это их вызовы, о формате они не знают: позы (`rig.savePos`/`loadPos`), опции модулей (`<модуль>_mod.options` у brows, eyelids, mouth, fishTail, fishWing), списки имён в `parents.py`. Везде словари и списки чисел/строк — родные для json типы. То есть переход — это правка в одном файле строк на двадцать, а не рефакторинг.

Инструмент раздаётся бесплатно и сцены ходят между людьми, так что «чужих сцен не бывает» — не тот случай.

**Как чинить:** `json` вместо `pickle`. По типам формат совместим (словари чисел и строк), нужен только путь миграции для существующих сцен: пробовать `json.loads`, при неудаче — старый `pickle`, и перезаписывать в json.

### 4. `if not state:` вместо `if state is None:` — восемь методов переключения

### 5. `.replace()` по именам нод заменяет все вхождения

75 мест. Самое опасное — [rig.py:409, 411](../rig.py#L409):

```python
tw_j = tw_name.replace("mod", "outJoint")
```

Подстрока `mod` встретится в любом имени вроде `model_...` или `modifier_...`, и имя развалится. То же с `.replace("skinJoint", "outJoint")` в [utils.getModuleName()](../utils.py#L385) и ещё в ~70 местах: если сегмент повторяется дважды, заменятся оба.

**Как чинить:** для суффикса — срез по длине или `rsplit(sep, 1)`, не `replace`.

### 6. `getModuleName()` молча берёт первый из одноимённых объектов

[utils.py:394](../utils.py#L394)

```python
path = cmds.ls(j, l=1) or []
if path:
    moduleName = path[0].split("rig|modules|")[-1].split("_mod|")[0]
```

Maya допускает одинаковые короткие имена под разными родителями. При дубликате функция берёт `[0]` — произвольный из двух — и возвращает чужой модуль, без всякого предупреждения. Именно так проявлялась ошибка симметрии ([main.py:2409](../main.py#L2409), исправлена 2026-08-28): дубликаты `l_fingers_*` появились задолго до падения, а упало на первом `listRelatives` по короткому имени.

### 7. `cmds.listRelatives(...)[0]` без проверки — 93 места

При отсутствии детей или родителя `listRelatives` возвращает `None`, и `[0]` даёт `TypeError: 'NoneType' object is not subscriptable` — трейсбек вместо внятного сообщения. Без `or []`, в отличие от соседнего `getSetObjects()` ([utils.py:429](../utils.py#L429)), где проверка есть. Вызывается из `module.rename()` ([module.py:923](../module.py#L923)) — переименование модуля с пустым `_sets` даст трейсбек. Всего 25 мест с `cmds.sets(..., q=1)` без защиты.

### 9. `self.curTwistName` после `twists_add()` указывает на зеркальный твист

[twist.py:331](../twist.py#L331) присваивается до рекурсивного создания зеркала ([twist.py:378](../twist.py#L378)), поэтому после возврата в переменной лежит имя правого твиста. `attach()` берёт цель именно оттуда ([twist.py:619](../twist.py#L619)), и при загрузке темплейта ([template.py:594](../template.py#L594)) команда уходит не тому твисту. Вдобавок ветка «привязать зеркало» внутри `attach()` не срабатывает, потому что имя уже начинается с `r`.

Сейчас не проявляется: у твистов лимба orient target совпадает с target, и `attach()` не вызывается. Проявится на твисте с нестандартной привязкой.

### 10. Блок переименования родителей в темплейте не работает для модулей со стороной

[template.py:427](../template.py#L427)

```python
if not mData["parent"].split("_")[1].isdigit():
    old_parent_module_name = mData["parent"].split("_")[0]
```

Для `l_arm_end_outJoint` берётся `split("_")[0]`, то есть `"l"`. Такого модуля в словаре нет, и переименование не происходит. Работает только для модулей без префикса стороны. Внешний `if mData["name"] == modulesRename[old_name]` вдобавок ограничивает проход теми модулями, которые переименовали сами, — родитель переименованного, но сам не переименованный, не обрабатывается.

### 11. `utils.oneStepUndo` теряет идентичность функции

[utils.py:1334](../utils.py#L1334)

```python
def oneStepUndo(func):
    def wrapper(*args, **kwargs):
        cmds.undoInfo(openChunk=True)
        func(*args, **kwargs)
        cmds.undoInfo(closeChunk=True)
    return wrapper
```

Три отдельные проблемы:

- нет `functools.wraps` — у декорированных функций теряются `__name__`, `__doc__`, `__wrapped__`, ломается интроспекция и отладка;
- **результат не возвращается** — любая декорированная функция всегда отдаёт `None`, даже если внутри есть `return`;
- нет `try/finally` — при исключении `closeChunk` не вызывается, и undo-стек Maya остаётся с открытым чанком.

### 12. Незакрытые чанки undo при исключении

Тот же класс, но россыпью: `cmds.undoInfo(openChunk=True)` … `closeChunk` без `try/finally`. Например [main.py:2295](../main.py#L2295) `disconnectModule`, [main.py:2093](../main.py#L2093) `deleteModule`, [main.py:2249](../main.py#L2249) `connectModule`. Любая ошибка в середине оставляет чанк открытым, и следующий Ctrl+Z откатывает не то, что ожидается.

## Архитектура

### 13. `main.py` — один класс на 3846 строк

`MainWindow`, 90 методов, в которых смешаны разметка UI (`initUi` — 342 строки), подключение сигналов (`connectSignals` — 147), операции над ригом (`makeSymmetryModule` — 211, `replaceModule` — 128, `deleteModule` — 126), работа с темплейтами, контролами и родителями. Логика рига неотделима от Qt, поэтому ничего из этого нельзя вызвать без окна — ни из скрипта, ни из теста.

### 14. Глобальные имена верхнего уровня

[rig.py:114](../rig.py#L114) — `rig`, `geo`, `modules`, `skeleton`, `twists` создаются с фиксированными именами в корне сцены, и весь код обращается к ним по строке. Следствия: два рига в одной сцене невозможны, риг из референса не виден, любой посторонний объект с именем `geo` ломает загрузку.

### 15. Имена нод как единственная структура данных

Связи между сущностями выражены исключительно конкатенацией строк: `self.name + "_thumbFinger_1_group_decMat"`. Нет ни карты имён, ни поиска по атрибутам или через `message`. Отсюда растут п. 5, п. 6, п. 3 и разбор строк вида [utils.py:369](../utils.py#L369) `path.split("|")[4]` — жёсткий индекс глубины DAG, который сломается при любом изменении вложенности.

### 16. Дублирование между вариантами модулей

`limb` (284), `limbQuadrupped` (306), `limbCurved` (268), `limbSimple` — почти одинаковый код с расхождениями в деталях. Правку приходится вносить в каждый, и, как показала история с оффсетами твистов, легко забыть один. То же в семействах `brows` / `brows2` / `browsCurved` / `browsSurf` / `browsSurf2` / `browsSimple` и `eyelids` / `eyelidsSimple` / `_eyelids2`.

### 17. Ядро не перезагружается по флагу Debug

`utils.isDebug()` включает `importlib.reload` только для `modules/<type>/<type>.py` ([utils.py:227](../utils.py#L227)). Правки в `twist.py`, `template.py`, `module.py`, `utils.py`, `main.py` требуют перезапуска Maya. Это не баг, но регулярный источник ложных выводов при отладке — на этом уже терялся круг проверок.

## Если чинить, то в таком порядке

1. ~~**П. 1** (удаление сетов)~~ — сделано частично: производные типы больше не трогаются. Остаток (пользовательские сеты выделения) в текущем процессе не проявляется, см. контекст в разделе «Охват».
2. **П. 11** (`oneStepUndo` без `wraps` / `finally` / `return`) — четыре строки, а чинит целый класс странного поведения undo и потерянных возвращаемых значений.
3. **П. 4** (`if not state`) — восемь однострочных правок, возвращает работоспособность аргумента.
4. **П. 8** (`getSetsInSet`) — одна строка, убирает падение при переименовании.
5. **П. 2** (`pickle` → `json`) — отложено по решению от 2026-08-28. Когда дойдёт очередь: чтение — сначала `json.loads`, при неудаче старый `pickle.loads` (старые сцены читаются, при следующем сохранении переезжают сами, отдельная миграция не нужна); запись — `json.dumps`, при несериализуемых данных откат на `pickle` с варнингом, чтобы не терять молча.
